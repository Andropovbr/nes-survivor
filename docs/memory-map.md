# Memory map and budgets

Measurements below come from `build/nes-survivor.map` generated by cc65 2.19
after the automatic-sword milestone. Regenerate the map after every
significant system is added.

## CPU address space and internal RAM

| Range | Bytes | Current purpose |
| --- | ---: | --- |
| `$0000-$0001` | 2 | deliberately unallocated zero page |
| `$0002-$001D` | 28 | project and cc65 zero-page symbols |
| `$001E-$00FF` | 226 | currently unallocated zero page |
| `$0100-$01FF` | 256 | 6502 hardware stack (worst-case reservation) |
| `$0200-$02FF` | 256 | page-aligned OAM shadow, 64 sprites x 4 bytes |
| `$0300-$0324` | 37 | cc65 initialized runtime data |
| `$0325-$0334` | 16 | C BSS globals |
| `$0335-$04FF` | 459 | free general RAM in the current linker region |
| `$0500-$07FF` | 768 | cc65 software parameter stack |

Static/reserved internal RAM is 1,361 of 2,048 bytes, leaving 687 bytes
unassigned (228 zero-page bytes and 459 general bytes). Stack ranges are budgets,
not measured high-water usage; future milestones must measure actual stack depth.

The OAM pool has exactly 64 entries, four bytes each, and is always DMA-uploaded
as one page. Every byte begins as `$FF`, so unused sprites have offscreen Y and
cannot appear. Future OAM construction must preserve deterministic priority and
hide every unused entry.

## Current mutable state

| State | Bytes | Location/segment |
| --- | ---: | --- |
| NMI frame counter | 1 | zero page `$0002` |
| controller read temporary | 1 | zero page `$0003` |
| cc65 zero-page runtime | 26 | zero page `$0004-$001D` |
| game state and OAM renderer cursor | 2 | BSS |
| input current/pressed/released | 3 | BSS |
| RNG state | 2 | BSS |
| player position/facing/moving/playback | 7 | BSS |
| sword active/cooldown timers | 2 | BSS |

The player and one sword runtime have no pools. There are no nametable
update buffers, audio allocations or heap. Heap allocation is prohibited. The
native 6502 stack remains isolated from OAM, and the cc65 software stack grows
within its dedicated three-page region.

The generic OAM renderer owns no sprite buffer beyond the existing 256-byte
shadow. It uses one BSS byte for the next entry, hides all 64 Y coordinates each
game frame, and emits the current player frame into entries 0-6. During the 12
active attack frames, the sword uses entries 7-8; otherwise those entries and
the remaining 55 stay hidden. The player uses at most three sprites on one
scanline, and the one-tile-wide sword adds at most one on the same scanline.

## Cartridge usage

| Region | Used content | Capacity | Notes |
| --- | ---: | ---: | --- |
| iNES header | 16 bytes | 16 bytes | mapper 0, NROM-256, horizontal mirroring |
| PRG-ROM | 3,252 bytes | 32,768 bytes | 9.92% used; 29,516 bytes free |
| CHR-ROM | 208 assigned bytes | 8,192 bytes | tile indexes `$00-$0C`; 7,984 bytes remain blank |
| Total `.nes` file | 40,976 bytes | 40,976 bytes | header + PRG + CHR |

PRG usage includes 220 bytes startup/palette data, 12 bytes constructor startup,
2,852 bytes code/runtime helpers, 125 bytes Soldier/sword RODATA,
37 bytes of DATA load image, and six interrupt-vector bytes. The animation
RODATA consists of 21 four-byte metasprite tiles, 3 four-byte frame records,
two seven-byte animation definitions, one seven-byte aggregate descriptor and
the sword's two four-byte metasprite records.
Fill bytes occupy the rest of the fixed NROM image but are not counted as used
content.

`assets/game.chr` occupies the required full 8 KiB bank. Soldier uses indexes
`$00-$07`, and the sword uses two 16-byte tiles at `$08-$09`. The highest
assigned imported tile remains `$0C`, for 208 assigned bytes total.

## VBlank budget

NMI always performs one OAM DMA and constant bookkeeping. Its worst-case estimate
is approximately 583 CPU cycles including interrupt entry, or about 26% of NTSC
VBlank. Soldier's palette is loaded only during reset with rendering disabled;
there are no palette, nametable or audio transfers during NMI. Any future
transfer queue must be bounded and added to this budget.
