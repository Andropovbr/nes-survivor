# Memory map and budgets

Measurements come from `build/nes-survivor.map`, generated by cc65 2.19 after
adding the fixed XP-gem pool.

## CPU address space and internal RAM

| Range | Bytes | Current purpose |
| --- | ---: | --- |
| `$0000-$0001` | 2 | deliberately unallocated zero page |
| `$0002-$001D` | 28 | project and cc65 zero-page symbols |
| `$001E-$00FF` | 226 | currently unallocated zero page |
| `$0100-$01FF` | 256 | 6502 hardware stack reservation |
| `$0200-$02FF` | 256 | page-aligned OAM shadow, 64 sprites x 4 bytes |
| `$0300-$0324` | 37 | cc65 initialized runtime data |
| `$0325-$03A0` | 124 | C BSS globals |
| `$03A1-$04FF` | 351 | free general RAM |
| `$0500-$07FF` | 768 | cc65 software parameter stack |

Static/reserved internal RAM is 1,469 of 2,048 bytes, leaving 579 bytes
unassigned: 228 zero-page bytes and 351 general bytes. Stack ranges are budgets,
not measured high-water usage.

## Mutable state and pools

| State | Bytes | Location/segment |
| --- | ---: | --- |
| NMI frame counter/controller temporary | 2 | zero page `$0002-$0003` |
| cc65 zero-page runtime | 26 | zero page `$0004-$001D` |
| OAM cursor | 1 | BSS |
| initial game state, countdown and blink flag | 3 | BSS |
| pending title-prompt NMI update | 1 | BSS |
| input current/pressed/released | 3 | BSS |
| RNG state | 2 | BSS |
| player position/facing/movement/playback | 7 | BSS |
| sword active/cooldown timers | 2 | BSS |
| Bat pool | 48 | BSS, 12 entries x 4 bytes |
| Bat shared spawn/movement/animation/separation/collision state | 15 | BSS |
| XP gem pool | 40 | BSS, 8 entries x 5 bytes |
| XP gem high-water mark and collection cursor | 2 | BSS |

Each Bat slot stores pixel X/Y, an active flag and horizontal facing. A shared Q4 accumulator emits
pixel movement steps, and a shared frame/timer animates all Bats synchronously.
Allocation reuses the first inactive slot below a shrinking high-water mark.
When all 12 slots are occupied, a due spawn remains pending and retries later;
no memory is overwritten and no scheduled Bat is silently discarded.
The eight separation bytes hold a rotating pair cursor plus one pending bounded
one-axis result; no per-Bat separation state is allocated.

Each gem slot stores X/Y, activity and a 16-bit represented-drop count. A full
pool condenses a new drop into the nearest active gem. Collection scans one slot
per frame and can take at most eight frames with a full pool.

## OAM budget

OAM priority is deterministic. Soldier uses entries 0-6. During its 12 active
attack frames the sword uses 7-8; otherwise Bats begin at 7. Up to 12 Bats use
two sprites each, followed by up to eight one-sprite gems. The worst case is
41/64 entries and 23 remain hidden. Overlapping objects may exceed the NES limit
of eight sprites per scanline. Player, active sword and enemies retain priority;
flicker rotation is not implemented.

## Cartridge usage

| Region | Used content | Capacity | Notes |
| --- | ---: | ---: | --- |
| iNES header | 16 bytes | 16 bytes | mapper 0, NROM-256 |
| PRG-ROM | 7,994 bytes | 32,768 bytes | 24.40%; 24,774 bytes free |
| CHR-ROM | 608 meaningful tile bytes | 8,192 bytes | 21 sprite tiles + 17 nonblank uppercase glyphs |
| Total `.nes` file | 40,976 bytes | 40,976 bytes | header + PRG + CHR |

PRG usage includes 220 startup bytes, 12 constructor-startup bytes, 7,500
code/runtime bytes, 219 RODATA bytes, 37 DATA-image bytes and six vector bytes.
This change adds 951 PRG bytes and 43 BSS bytes relative to the documented
baseline; zero page, DATA, OAM shadow and stacks are unchanged.

The first 4 KiB of `assets/game.chr` supplies sprites: Soldier uses `$00-$07`,
the animated sword `$08-$09`, Bat `$0A-$0D`, and the gem `$14`. `src/chr.s`
supplies 17 nonblank uppercase ASCII glyphs in the `$1000` background table at
their character codes; the reserved space tile and all unused patterns are blank.

## Timing budgets

NMI remains bounded to one OAM DMA plus constant bookkeeping, approximately 590
CPU cycles including interrupt entry when no VRAM update is pending. Showing the
11-tile title prompt costs approximately 788 cycles total; hiding it is cheaper.
Gameplay, collisions and OAM construction run outside NMI. OAM initialization
hides all 64 entries once; later construction hides only prior used entries.

Before optimization, the 850-frame stress case lost 171 gameplay updates after
the third Bat. The current 1,750-frame test compensates for the initial screens,
saturates all 12 Bat slots and observes 1,735 NMI-synchronized gameplay updates
after its post-transition baseline with no skipped update. Bat animation is
shared and rendering uses a measured, specialized two-sprite OAM path in C.

An initial full 66-pair separation pass lost 249 gameplay updates in the same
stress scenario. Capping the pass at 12 and then four pairs still lost 107 and
28 updates. The final version inspects one pair on a frame without a Q4 movement
step and applies its cached result on the next step. The current state-aware
stress scenario still reaches all 12 Bats without skipped gameplay updates.

Adding per-Bat facing initially repeated the render branch for both tiles and
lost four updates at 12 Bats with the sword active. Emitting the complete
two-sprite record through one facing branch preserves the zero-skip stress
result with horizontal flipping enabled.

The first gem integration scanned all eight pickup slots every frame and the
12-Bat stress lost eight gameplay updates during sword-active frames. Staggering
pickup checks alone did not restore the budget. Alternating even/odd enemy
hitbox indexes reduced the sword collision peak while checking every Bat within
two active frames. Final measurement: 1,750 video frames, 12 Bats, at least one
gem, 1,735 NMIs/updates and zero skipped gameplay updates. Cycle counts were not
profiled separately.

Full nametable transitions intentionally disable NMI and rendering while 1,024
bytes plus fixed text are written. The 450-frame Mesen runtime observed 435
NMIs, with the difference covering reset stabilization and the bounded screen
transitions. Blink updates now execute as one bounded NMI transfer without
toggling rendering; their cycle counts are generated-code estimates, not emulator
cycle-profiler measurements.
